# Candidate registry

The registry is the `candidates/` directory: one `<name>.yaml` file per candidate, and the only definition of it. No database table copies it. What a candidate is and how it is judged is on [Goal and strategy](../foundations/goal-and-strategy.md#candidates).

## File format

`odds_core.candidates.load_candidates` reads every `*.yaml` file in a directory with `odds_core.candidates.load_candidate_file`, validates it against `odds_core.candidates.Candidate` and returns the candidates sorted by name. A missing directory gives an empty list. Every model rejects unknown fields.

| Field | Model | Meaning |
|---|---|---|
| `name`, `description`, `sport`, `version`, `issue`, `start_date`, status | `odds_core.candidates._CandidateBase` | Shared by both kinds. `name` matches the file name and the pattern `odds_core.candidates.NAME_PATTERN`. `sport` is a [sport key](../collection/sport-and-market-keys.md). `issue` is the idea's GitHub issue. `start_date` is the first day it may place bets. The status is an `odds_core.candidates.CandidateStatus` |
| `kind: mechanical`, `market`, `rule`, `odds_core.candidates.MechanicalCandidate.rule_sha256` and params | `odds_core.candidates.MechanicalCandidate` | `market` is the market the rule decides, an `odds_core.vocabulary.Market` such as `1x2` or `totals` ([market keys](../collection/sport-and-market-keys.md)). `rule` names a rule function ([candidate rules](candidate-rules.md)). `odds_core.candidates.MechanicalCandidate.rule_sha256` is the hash of the rule's code ([rule pinning](candidate-rules.md#rule-pinning)), 64 lowercase hex characters, and required in the registry; a [draft](candidate-backtest.md#command) outside it may omit it. The parameters are a free JSON mapping here, validated against the rule's params model, and its hash checked against the rule's current one, by `odds_lambda.candidate_rules.pinning.validate_candidate_rules`; every rule requires `minutes_before_kickoff`, the list of decision times, and `max_input_age_minutes` ([rule interface](candidate-rules.md#rule-interface)) |
| `kind: agent` | `odds_core.candidates.AgentCandidate` | No further fields; the agent's prompts and model are its definition ([agent run](../agent/agent-run-job.md)) |

`odds_core.candidates.load_candidates` raises a `ValueError` naming the file when a file fails validation, its `name` differs from its file stem or a mechanical file lacks `odds_core.candidates.MechanicalCandidate.rule_sha256`, and when a sport has more than one agent candidate whose status is active or promoted. Agents for one sport share `packages/odds-mcp/agents/common.md` and the sport's `base.md`, so two live agents for one sport would run identical prompts. A killed agent does not count, so its replacement can be added.

A change of status goes through a pull request. The version is a strict positive integer (`"3"` is rejected), bumped whenever the rule, parameters or model change ([versioning](../foundations/goal-and-strategy.md#candidates)).

## `odds candidates list`

`odds_cli.commands.candidates.list_candidates` prints each candidate's name, kind, sport, version, status, start date and issue, optionally filtered by status. It reads the files in `odds_core.candidates.candidates_dir` and does not touch the database. It validates every mechanical candidate's rule and params with `odds_lambda.candidate_rules.pinning.validate_candidate_rules`. An invalid registry or rule prints the error in red and exits 1.

## `odds candidates rule-hash`

`odds_cli.commands.candidates.rule_hash` prints `odds_lambda.candidate_rules.pinning.rule_sha256` for a rule name (the hash of every first-party module the rule's code imports, from the rule function through the code that loads, picks and prices its inputs and, for a model rule, the code that fits and queries its model, and of the sharp inputs and extra markets it needs, [rule pinning](candidate-rules.md#rule-pinning)), the value a mechanical candidate records as `odds_core.candidates.MechanicalCandidate.rule_sha256`. An unknown rule name prints the known names and exits 1.

## `odds candidates report`

`odds_cli.commands.candidates.report` prints one row per candidate version: settled bets, bets with a close, bets without one, pending bets, stake, P&L, ROI and the family size k, the checkpoint the verdict rests on (n, mean EV, the 95% CI, the promote CI with its confidence level) and the verdict. It reads the database through `odds_analytics.candidate_report.candidate_report` and the registry files. That function reads the trades and the first decision of every version once and summarises them with `odds_analytics.candidate_report.report_candidates` on an optional executor, which the [web UI](../operations/odds-web.md) holds to one thread. The command, `odds_mcp.server.get_portfolio` and the web UI all call it; the command and `odds_mcp.server.get_portfolio` take only its summaries. Every registered candidate appears, with zero bets before it trades, and so does any (name, version) with trades whose version differs from the registry's (or whose candidate is absent from it), shown as "not current".

`odds_mcp.server.get_portfolio` returns the same summaries as `candidates`, from the same function. The trades behind them come from the agent and from the [run-candidates job](run-candidates-job.md). When the registry is invalid it returns `{"error": <message>}` there and the rest of the portfolio unchanged.

What is scored, in `odds_analytics.candidate_report`:

- **Bets.** `odds_analytics.candidate_report.ScoredBet` is what is scored, built from an `odds_core.paper_trade_models.PaperTrade` (its event an integer id) or from a [replayed](candidate-backtest.md) bet. `odds_analytics.candidate_report.load_scored_trades` takes every paper trade that carries a candidate, settled or not, in placement order (`placed_at`, then id), drops void ones, and reads the closes of their events per market with `odds_analytics.candidate_report.close_probabilities` ([paper trading](../agent/paper-trading.md#candidate-fields)). The sharp reading an agent's trade records at placement is not scored ([sharp fields](../agent/paper-trading.md#sharp-fields)). Pushes count as settled bets.
- **Close.** `p_close` is the devigged probability of the trade's selection in `odds_core.close.event_close`, computed from the event's stored prices when the report runs, so nothing is recorded at settlement and the close can be re-derived. `odds_core.close.close_quotes` loads only the quotes that can be the close, for all the events of each sport: the Betfair Exchange backs of live Betfair snapshots within `odds_core.close.LIVE_CLOSE_WINDOW` before each event's kick-off, and the quotes of the sport's `odds_core.close.FallbackSpec` (the Betfair Exchange backs of FDUK closing snapshots for a football league; for NBA the Polymarket mids and back prices observed within the same window, [ADR-0019](../../docs/adr/0019-nba-h2h-close-betfair-with-polymarket-fallback.md)). An event of a sport with no close for the market has no quotes. The [health monitor's missing-close check](../operations/health-monitor.md) uses the same close. `odds_core.close.CLOSES` holds every (sport, market) a candidate can decide, and those whose entry is not `None` have a close (`odds_analytics.candidate_report.selection_close_probability`): `1x2` and `totals` of EPL, the Championship, La Liga, Serie A, the Bundesliga and Ligue 1, and NBA `h2h`. It is taken on the selection's line: `odds_core.close.event_close` picks among the exchange prices on that line only. An MLB `h2h` trade has none, nor has an NBA spreads or totals trade, and neither has a trade whose event has no close on its line. The report loads the close quotes of each market its trades are on and reads each trade's close on the trade's own line, `None` in a market without lines ([paper trading](../agent/paper-trading.md#the-paper_trades-table)).
- **EV.** `odds_analytics.candidate_report.ScoredBet.ev` is `odds_analytics.candidate_report.expected_value` of `p_close` and the price: `p_close × price_decimal − 1`.
- **Scoreable prefix.** `odds_analytics.candidate_report.scoreable_prefix` walks a version's trades in placement order and stops at the first trade that is unsettled, or has no close and kicked off less than its `odds_analytics.candidate_report.ScoredBet.close_grace` before the report's `now`, since a fallback close may still arrive: 7 days for an EPL trade, whose FDUK closing price can be stored that late, and none for an NBA trade, whose Polymarket price is stored before kick-off (`odds_core.close.close_grace`). A trade with no close after that is final: it counts in P&L and in the no-close count, and is left out of the EV. Trades beyond the prefix are the pending count. The prefix only grows, and the bets with a close in it keep their order, so a checkpoint's bets never change once reached.
- **Checkpoint.** `odds_analytics.candidate_report.checkpoint_at` scores the first n bets with a close, the earliest, for n a multiple of `odds_analytics.candidate_report.CHECKPOINT_SIZE` (100). The score is the stake-weighted mean EV per unit staked, `Σ stake·EV / Σ stake`, with `odds_analytics.retail_ev_metrics.event_clustered_ratio` giving percentile CIs at the 95% kill level and the promote level (below) from `odds_analytics.candidate_report.DEFAULT_BOOTSTRAP_SAMPLES` resamples of whole events under a fixed seed, so the same trades always give the same verdict.
- **Family size k.** `odds_analytics.candidate_report.family_starts` lists when each version of the candidate's family, the mechanical candidates with its `rule`, `sport` and `market` (`odds_analytics.candidate_report.family`), took its first look, and `odds_analytics.candidate_report.family_size_at` counts those by a time (at least 1). A version counts from its first `odds_core.paper_trade_models.CandidateDecision.decision_time`, the minimum per name and version that `odds_analytics.candidate_report.load_decision_starts` reads, for names whose registry entry is in the family. A registered version that has not decided counts for nothing, and the registry `start_date` is not used, so [a version counts from its first recorded decision](../foundations/goal-and-strategy.md#how-a-candidate-is-judged). Earlier versions are not in the registry (a version bump overwrites the file), and their decisions are what remains of them. Every version of a name takes the family of its registry entry; a name absent from the registry, and an agent candidate, has k = 1. A checkpoint's k is the size at the placement of its nth bet (`odds_analytics.candidate_report.ScoredBet.placed_at`), so later versions do not change an earlier checkpoint. `odds_analytics.candidate_report.CandidateSummary.family_versions` is the verdict checkpoint's k, or the size now before any checkpoint, and `odds_mcp.server.get_portfolio` returns it.
- **Verdict.** `odds_analytics.candidate_report.judge` evaluates checkpoints 100, 200, … in order, each at the k of its nth bet, and returns the first `odds_analytics.candidate_report.Verdict` that fires, with the checkpoint's n: `promote` when the lower bound of the promote CI is above zero, at confidence `odds_analytics.candidate_report.promote_level` (1 − `odds_analytics.candidate_report.PROMOTE_ERROR` / k); `kill` when the 95% CI's upper bound is at or below zero, or at the `odds_analytics.candidate_report.KILL_AT_BETS` (500) checkpoint without promotion. Later bets do not reverse it. With neither it returns `continue` at the last checkpoint reached, and `not_yet` below 100 bets with a close. It returns every checkpoint evaluated up to the verdict, and each is frozen once reached: `odds_analytics.candidate_report.CandidateSummary.checkpoints` holds them and `odds_analytics.candidate_report.CandidateSummary.checkpoint` is the last. The rules and their rationale are on [Goal and strategy](../foundations/goal-and-strategy.md#how-a-candidate-is-judged). The verdict is advice: a status change is still a pull request.
- **Current estimate.** `odds_analytics.candidate_report.current_estimate` scores every bet with a close, at the family size now, as `odds_analytics.candidate_report.CandidateSummary.current`. It is a read of where the version stands, not a verdict: it moves with every bet, is `None` below `odds_analytics.candidate_report.MIN_CURRENT_EVENTS` events with a close, and is the verdict's checkpoint itself when both score the same bets at the same k. `odds candidates report` and `odds_mcp.server.get_portfolio` do not print it; the [web UI](../operations/odds-web.md#portfolio-page) draws it.
- **Registered version.** `odds_analytics.candidate_report.CandidateSummary.registered` is the registry's entry at exactly the summary's name and version, `None` for a version the registry does not hold: a version bump overwrites the file, so an earlier version's kind, sport and market are not recorded anywhere and the current entry's are not its own. `odds_analytics.candidate_report.CandidateSummary.status` is its registry status (active, promoted or killed), apart from the statistical verdict, and `None` there. `odds_analytics.candidate_report.summarize_candidate` takes the entry; a replay passes the draft. `odds_analytics.candidate_report.unscored_version` is the empty summary and running score of a version the report omits (no trades, not in the registry), which the web UI shows only if the version recorded decisions.
- **Checkpoint progress.** `odds_analytics.candidate_report.next_checkpoint` is the first checkpoint with more bets than a version has with a close, capped at `odds_analytics.candidate_report.KILL_AT_BETS`. `odds_analytics.candidate_report.checkpoint_progress` gives it with how far the count is from the checkpoint before (`odds_analytics.candidate_report.CheckpointProgress`), 0 just after one and 1 at the next, and `odds_analytics.candidate_report.checkpoints_through_next` lists every checkpoint up to it. The [web UI](../operations/odds-web.md) draws its progress bars and checkpoint lines from these.
- **Running score.** `odds_analytics.candidate_report.running_score` gives the stake, Σ stake·EV and P&L so far after each bet with a close in the scoreable prefix (`odds_analytics.candidate_report.RunningScore`). Its `odds_analytics.candidate_report.RunningScore.mean_ev` at n is the score of the checkpoint or current estimate over the same n bets. `odds_analytics.candidate_report.report_candidates` returns each version's running score beside the summaries, from the same trades and `now`, as `odds_analytics.candidate_report.CandidateReport`. Only the [web UI's candidate page](../operations/odds-web.md#candidate-page) draws it.

## Replay commands

`odds_cli.commands.candidates.backtest` replays a rule over completed events, tuning a model rule's model on its training matches and refitting it as it goes, and recording the library versions that fit it, and scores it with the functions above, optionally beside a second candidate, never a model rule, on the same matches ([replay backtest](candidate-backtest.md)). It is the only command that runs a [model rule](candidate-rules.md#model-rules). `odds_cli.commands.candidates.parity` replays each recorded decision from its recorded input snapshots and compares the bets ([parity check](candidate-parity.md)). The steps that use them are on [From idea to verdict](howto-take-an-idea-to-a-verdict.md).

## Version check

`scripts.check_candidate_versions.check` compares the working tree's `candidates/*.yaml` with the same files at a base commit. It runs as the `candidate-versions` pre-commit hook ([code conventions](../foundations/code-conventions.md#mechanical-gates)), locally and in the `Lint` workflow. The base is `--base`, else the merge-base of `HEAD` with `origin/main`, else with `main`, else `HEAD`.

It fails when:

- a file that exists at the base is deleted. A candidate is killed by setting its status to killed. A rename reads as a deletion, so it fails: a renamed candidate is a new candidate;
- a file is not valid YAML (the error names the file);
- a file's `version` decreased;
- any key other than the status and `description` changed and the version did not increase (`UNVERSIONED_KEYS` in the script), unless the file at the base has a `start_date` later than today (UTC). A candidate that has not started has made no decisions, so any key may change at the same version. A missing or non-date `start_date` at the base does not qualify, and deletion and a version decrease still fail.

A new file always passes. The check compares YAML only. A mechanical rule's code is pinned by the `odds_core.candidates.MechanicalCandidate.rule_sha256` in the file ([rule pinning](candidate-rules.md#rule-pinning)), so a code change reaches this check as a change to that key.

A `odds_core.candidates.MechanicalCandidate.rule_sha256` may also change at the same version when the rule and its old and new hashes are a complete row of the [rehash ledger](#rehash-ledger); any other key that changed still needs a new version, and without a matching row so does the hash. Changes to an agent's prompts or model are not enforced by it.

## Rehash ledger

The ledger file in `candidates/`, named by `odds_core.rehash_ledger.REHASH_LEDGER`, records the hash changes that leave every bet the same, one JSON object per line, an `odds_core.rehash_ledger.Rehash`:

- the rule, its old hash (at the base commit) and its new hash (at the head commit), and both commit SHAs;
- the replay's kick-off days, the database it read (role, host, port and name, no password) and the sha256 of the replay output;
- the GitHub PR or issue of the change;
- per candidate of the rule (`odds_core.rehash_ledger.RehashCandidate`), its version, its decisions with inputs and its bets in the replay, and the recorded decisions the parity check matched, of all of them.

`odds_core.rehash_ledger.load_rehashes` reads it. Paper trades, decisions, the report and the parity check key a candidate by name and version, never by hash, so a candidate's forward test continues across a rehash.

The [version check](#version-check) validates each row with `odds_core.rehash_ledger.Rehash` itself, loading `odds_core.rehash_ledger` from its file (it imports only pydantic), and accepts a row only when every field is present and well formed: commit SHAs, a non-empty range and database, a decision for each candidate, a bet in all, and parity matched for every recorded decision. A candidate with no recorded decisions is recorded as 0 of 0. The hook cannot rerun the replay in CI. The ledger is a record the rehash command makes, not a proof, and review of the PR that adds a row is what trusts it.

`odds_cli.commands.candidates.rehash` (`odds candidates rehash <rule> --database-url <url> --from <day> --to <day> --evidence <link> [--base <revision>]`) writes a row through `odds_analytics.candidate_rehash.rehash`. It refuses, writing nothing and exiting 1, at the first of these that fails:

1. The range runs forwards, no other rehash holds the repository's lock, and the working tree has no uncommitted change outside `candidates/`, so the head commit is the code replayed.
2. Every registered candidate of the rule records one hash. When all record the current hash, there is nothing to do.
3. It opens a read-only repeatable-read transaction on the database and exports its snapshot (`odds_analytics.candidate_rehash.frozen_snapshot`). Both replays and the parity checks read that one snapshot.
4. It replays every candidate of the rule with `scripts.replay_candidates` under the base revision's code (`--base`, by default the merge-base of `HEAD` with `origin/main`, resolved to a commit SHA), checked out in a temporary git worktree in `worktrees/`, and computes the rule's hash there. That hash must be the one the candidates record.
5. It replays them again under the head's code, whose hash must be the current one. The two outputs, every decision's counts, bets and backtest summary as canonical JSON, must be byte-identical.
6. Each candidate needs a decision with inputs in the replay, and the replay needs a bet. The [parity check](candidate-parity.md) of each candidate must match every recorded decision.

It then writes each candidate file's `odds_core.candidates.MechanicalCandidate.rule_sha256` in place, keeping the file's other lines and any comment on that line (`odds_analytics.candidate_rehash.staged_file`). It refuses unless exactly one plain `odds_core.candidates.MechanicalCandidate.rule_sha256` line changes and the edited file parses to the new hash, and reloads every written file to check it records the new hash. Then it appends the row last. A failure between the two leaves a hash change without its row, which the version check rejects.

On the production host, pass `WEB_DATABASE_URL`, the read-only `odds_web` role ([odds-web](../operations/odds-web.md#database-access)), as `--database-url`: `odds copy from-prod` copies no decisions or trades, so parity can only be checked there. The steps that use it are on [From idea to verdict](howto-take-an-idea-to-a-verdict.md).
