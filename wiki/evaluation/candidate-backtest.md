# Replay backtest

`odds candidates backtest <name-or-path> --from YYYY-MM-DD --to YYYY-MM-DD` replays a [mechanical candidate's](candidate-registry.md) rule over the completed events of its leagues and scores the bets with the code the forward-test report uses. Development data can kill an idea and never promotes one ([goal and strategy](../foundations/goal-and-strategy.md#how-a-candidate-is-judged)); the task is on [From idea to verdict](howto-take-an-idea-to-a-verdict.md).

## Command

`odds_cli.commands.candidates.backtest` resolves its argument with `odds_cli.commands.candidates._resolve`: a path to an existing file loads that file, and any other argument is a registered candidate name. `--from` and `--to` are UTC days, both inclusive. `--json <path>` also writes the result as JSON. `--compare <name-or-path>` also replays a second candidate, resolved the same way, on the events the first decided ([comparison](#comparison)). An unknown candidate, an agent candidate, a bad date, `--to` before `--from` or an invalid rule or params prints the error and exits 1.

A file loaded by path may be an unregistered draft. `odds_core.candidates.load_candidate_file` parses it with the registry's model, but does not require the file name to match `name` and does not require `odds_core.candidates.MechanicalCandidate.rule_sha256`. `odds_analytics.candidate_backtest.hash_status` reports whether the recorded hash is `match`, `mismatch` or `absent` against the rule's current hash, `odds_lambda.candidate_rules.pinning.rule_sha256`, or `unhashable` when the rule's closure fails closed ([rule pinning](candidate-rules.md#rule-pinning)), and the command prints a warning unless it matches. The registry rejects a mechanical file without the hash.

## Sealed holdout

The 2025-26 season (1 August to 31 July) of the Championship, La Liga, Serie A, the Bundesliga and Ligue 1 is sealed (`odds_analytics.holdout.holdout_windows`, [ADR-0021](../../docs/adr/0021-sealed-holdout-and-one-shot-gate.md)). EPL has no sealed window: its seasons are development data ([ADR-0024](../../docs/adr/0024-epl-2022-24-is-development-data.md)), so a pre-registration that lists it runs on its other leagues and records EPL as a league without a window.

**The seal.** `odds_analytics.candidate_backtest.final_events` and `odds_analytics.candidate_backtest.collect`, which `odds_analytics.candidate_backtest.replay` and every other replay reach, call `odds_analytics.holdout.require_clear`. A range that touches a sealed window of any of the candidate's leagues raises `odds_analytics.holdout.HoldoutRefused` before any query, so the development backtest (with `--compare`: each candidate is checked) exits 1 on such a range, mixed ranges included, and `scripts.replay_candidates.dump` replays only each league's days outside its windows (`odds_analytics.holdout.development_segments`, passed by the rehash command as `--segments`). The rehash passes both replays the same days: those outside the windows of both the base revision (`odds_analytics.candidate_rehash.windows_under`) and the working tree (`odds_analytics.candidate_rehash.development_ranges`), so a seal change between them refuses neither. Only an `odds_analytics.holdout.HoldoutAccess` for the league's window opens it, and only `odds_analytics.holdout.Reservation.access` issues one.

**The command.** `odds candidates holdout <selection file>` (`odds_cli.commands.candidates.holdout_command`, `odds_analytics.holdout_run.run_holdout`) runs a [selection and its grid](candidate-registry.md#sealed-holdout-files) once:

1. `odds_analytics.holdout.load_plan` checks both files: names are the identity (the grid file through `odds_analytics.holdout.load_preregistration`), the selection's `grid_sha256` is the grid file's content, the cell belongs to the grid (or is one of its listed cells) and at least one league has a sealed window (`odds_analytics.holdout.Plan.holdout_leagues`); a file none of whose leagues has one is refused. The pre-registration becomes one pooled draft over those leagues with the cell as params (`odds_analytics.holdout_run.pooled_draft`), whose rule is resolved, so a mistake costs no run. A league with no window (`odds_analytics.holdout.Plan.windowless_leagues`) is not replayed and contributes no bets.
2. Under an exclusive lock shared by every worktree (`odds_analytics.holdout.exclusive_lock`), `odds_analytics.holdout.reserve` requires each file committed, unchanged and touched by one commit (`odds_analytics.holdout.committed_once`), the grid file's older than the earliest Odds API `source_stamped` snapshot in the database read (`odds_analytics.holdout_run.earliest_backfill`) when there is one; a clean tree; and a committed ledger that extends `origin/main`'s and holds no row for the issue, market and version. It then spends the identity in the spent file of the git common directory (`odds_analytics.holdout.SPENT_FILE`, shared by every worktree), syncing the file and its directory so the spend survives a power loss, and appends and syncs a `reserved` row.
3. `odds_analytics.candidate_backtest.collect` replays the draft once, each league on its own sealed window with that league's access.
4. The draft's bets, one series across its leagues, are scored once with `odds_analytics.candidate_backtest.score` at family size 1; `odds_analytics.holdout.gate` judges the overall estimate: pass when mean EV is above 0 and the event-clustered 95% interval's upper bound is above 0; under `odds_analytics.holdout.MIN_GATE_BETS` (30) bets, the interval condition alone passes and the result is flagged; no bets fails, flagged.
5. A `result` row is appended, recording the leagues without a window (`odds_analytics.holdout.HoldoutResult.leagues_without_window`). An error after step 2 leaves the `reserved` row and the run is spent.

The command prints each window's coverage, the leagues without a window and the gate, and a holdout result never promotes. The selection it runs is written by [`odds candidates select`](cell-selection.md), which replays every cell of the grid on development data through the same `odds_analytics.candidate_backtest.collect`.

## Replay

`odds_analytics.candidate_backtest.replay` runs these steps.

1. **Events.** `odds_analytics.candidate_backtest.collect` takes each of the candidate's leagues' events from `odds_analytics.candidate_backtest.final_events`, the league's `FINAL` events with both scores and a kick-off within the days (a league's day ranges may not overlap, so no event is taken twice), and orders them together by kick-off and id, with no collapsing of events that name one match: the replay decides every such event, as the [run-candidates job](run-candidates-job.md#decisions) does.
2. **Decision times.** `odds_lambda.candidate_rules.rules.decision_times` of the event's kick-off: each entry of the params' `minutes_before_kickoff` with its time, decided earliest first. A completed event has only its final kick-off, so a rescheduled fixture is decided against its final time and not the one a live run saw ([parity check](candidate-parity.md) uses the recorded one).
3. **State.** At each decision time, `odds_lambda.candidate_rules.rules.run_rule` loads the state, within the params' maximum input age (and, for each lookback point, back to the point and its age, [lookback points](candidate-rules.md#lookback-points)), with `known_at=None` (a rule that declares [fixture inputs](candidate-rules.md#fixture-context) also gets them from the stored events, a previous result counting once its match kicked off three hours before the decision time and was completed by it, and the decision is counted without input when a team's previous result is unknown), so a snapshot counts when it is stamped at or before the decision time, whenever it was stored: backfilled rows were created long after their snapshot times ([as-of rules](candidate-rules.md#market-state)). The live runner and the parity check decide through the same function. The rule's sharp inputs and extra markets decide what is an input ([market state](candidate-rules.md#market-state), [extra markets](candidate-rules.md#extra-markets)): for a rule that needs the exchange, only a snapshot carrying UK retail prices and a Betfair Exchange price together (in practice live OddsPortal snapshots, and live Odds API ones that quote the exchange), and for a rule that needs Polymarket, also a Polymarket snapshot. A range before that collection, or one whose snapshots fall outside the params' maximum input age, has no inputs and no bets. A decision without inputs is what the live runner records as missed; the replay counts it in coverage.
4. **Bets.** The rule's bets, less those on selections an earlier decision time of the event already bet, as the live runner drops them ([once per selection](candidate-rules.md#once-per-selection)). Each bet is placed at its decision time, and the bets of every league are ordered together by it, then by kick-off, event and rule order, as the report orders paper trades by placement. Each is settled from the final score by `odds_core.odds_math.selection_won`, as `odds_lambda.paper_trading.settle_trades` settles paper trades: a `1x2` or `h2h` bet by the result, and a totals bet over when the goals exceed its line and under when they fall short (a half line cannot push); the profit comes from `odds_core.odds_math.calculate_profit_from_decimal`.
5. **Close.** Each bet's `p_close`, and its `p_close_power` (the same close devigged by the power method, for information, [report](candidate-registry.md#odds-candidates-report)), come from `odds_analytics.candidate_report.selection_close_probability` over the quotes `odds_core.close.close_quotes` loads for the candidate's market, as in the [report](candidate-registry.md#odds-candidates-report): the close on the bet's line, so a totals bet whose line has no close has none. A bet in a (sport, market) whose `odds_core.close.CLOSES` entry is `None`, such as every MLB bet, has none; a football league's `1x2` and `totals` bets have one from FDUK's Betfair Exchange close where no live Betfair snapshot is stored.

A [model rule](candidate-rules.md#model-rules) decides only part of the range, with its model refitted as the replay goes ([model rules](#model-rules)).

Events are processed in batches of `odds_analytics.candidate_backtest.EVENT_BATCH_SIZE`: one query per decision reads only the quotes within the maximum input age before its decision time, and the close quotes are read in two queries per batch for the events that have a bet.

## Model rules

For a model rule, `odds_analytics.candidate_backtest.replay` takes the range's events in kick-off order and leaves the first `training_matches` of them to training only, with any later match that kicks off at the same time as the last of them (`odds_analytics.candidate_model.training_prefix`): they are never decided. `odds_analytics.candidate_model.refit_blocks` splits the rest, the scored matches, into blocks of `refit_every_matches` in kick-off order; the last block may be partial. A range with no match after its training prefix scores nothing.

`odds_analytics.candidate_model.ModelReplay` first tunes the model's hyperparameters on the training matches that kicked off before the first scored decision time, the matches the first refit trains on, so every tuning label exists before any scored decision ([hyperparameters](candidate-rules.md#the-retail-ev-model-rule)); no scored match reaches the tuning, and a training match kicking off later is left out of it. It then refits the model before each block, at the block's earliest decision time, with those hyperparameters, on the [training rows](candidate-rules.md#the-retail-ev-model-rule) of every range match that kicked off before that time: the prefix and the earlier scored matches. A prefix match that kicks off after a scored match's first decision waits for a later block. Each match's rows are built once, from its quotes in the decision window (read with the sharp inputs of the rule's spec, `odds_lambda.candidate_rules.retail_ev_model.RETAIL_EV_MODEL`) and its close quotes (loaded together for the matches a tuning or refit first needs), and only a match with a live Betfair close has rows. A tuning or a refit without any training row raises `ValueError`, which the command prints before exiting 1. The block's matches are then decided as in [replay](#replay), steps 2 to 5, with the rule bound to that fit, so the model never sees a match before it is scored.

`odds_analytics.candidate_backtest.BacktestResult.tuning` records the chosen hyperparameters, the trial count, the tuning matches, the folds used with each one's validation row count, and the mean fold weighted MSE of the model and of the exchange-at-t baseline (`odds_analytics.candidate_model.Tuning`). `odds_analytics.candidate_backtest.BacktestResult.refits` records each fit (`odds_analytics.candidate_model.Refit`): its time, the matches with training rows, the row count and the scored event ids (integers). The command prints both as tables above the coverage.

## Comparison

`--compare` replays the second candidate over the same range with `only_events` (integer event ids) set to the first candidate's `odds_analytics.candidate_backtest.BacktestResult.decided_event_ids`: a model rule's scored matches, or every range event for a rule without a model. Its k is its own family's. The command prints its tables after the first candidate's, then one table with both candidates' estimates over every bet with a close. The command refuses a model rule as the second candidate, because it trains on its own range. The re-test of the retail-EV model compares its draft, `experiments/configs/candidate_retail_ev_model_epl.yaml`, with `exchange-gap-epl` this way ([#657](https://github.com/Acusick1/odds/issues/657)).

## Scoring

`odds_analytics.candidate_backtest.score` scores a pooled candidate's bets as one series, as the report does. It passes the bets, as `odds_analytics.candidate_report.ScoredBet`, to `odds_analytics.candidate_report.summarize_candidate` and the draft as the registered entry, with the family size k the command computes: the type, EV (`odds_analytics.candidate_report.expected_value`), prefix, checkpoint and verdict code that [the report](candidate-registry.md#odds-candidates-report) applies to paper trades. The summary also carries the report's current estimate and every checkpoint reached, which the backtest result includes beside its own overall estimate. All backtest bets are settled. The no-close grace (`odds_analytics.candidate_report.ScoredBet.close_grace`, `odds_core.close.close_grace`) is measured from the run time, so a range ending within 7 days of today leaves its last EPL bets pending. k is the versions with any recorded decision of the draft's family (the same rule and market, fixed for a name, leagues intersecting the draft's own, each recorded version by the leagues it decided with, [family size](candidate-registry.md#odds-candidates-report)), from `odds_analytics.candidate_report.family_starts` and `odds_analytics.candidate_report.family_size_at`, plus the draft as one more. A registered candidate that already has decisions is not counted twice ([family size](candidate-registry.md#odds-candidates-report)). One k applies to every checkpoint, since a replay has no placement history to count versions against. The command reads the registry with `odds_core.candidates.load_candidates` alone and the recorded decisions from the database, so a registered rule whose code changed since its hash was recorded does not stop a draft backtest. The bootstrap uses the same seed, so a replay gives the same numbers every time.

The checkpoint is the verdict's: the first 100, 200, … 500 bets with a close, which stop at the first time the verdict code reports the promote bar met or a kill. `odds_analytics.candidate_backtest.BacktestResult.overall` is a further estimate over every bet with a close in the scoreable prefix, for a range with more bets than the verdict looks at.

## Coverage

`odds_analytics.candidate_backtest.Coverage` counts, for the replayed events and their decisions (one per event and decision time):

| Field | Counts |
|---|---|
| `events` | Events decided: those in range, or for a model rule its scored matches (`odds_analytics.candidate_backtest.BacktestResult.range_events` counts the range, before any `only_events` filter) |
| `decisions` | Decisions: each event once per decision time |
| `with_input` | Decisions with every input the rule needs within the maximum input age at the decision time |
| `with_exchange` | Decisions with an exchange price at the decision time |
| `with_polymarket` | Decisions with a Polymarket price at the decision time; only a rule that needs Polymarket reads one |
| `with_retail` | Decisions with at least one UK retail quote at that time |
| `with_bet` | Decisions that placed at least one bet |
| `bets`, `bets_with_close` | Bets, and those with a close |

The command prints the verdict as `meets_promote_bar` (with "development data, not a promotion"), `kill`, `continue` or `not_yet`, never `promote`, and `--json` writes the same strings (`odds_cli.commands.candidates._backtest_verdict`). It prints these beside the no-close and pending counts, k, the checkpoint and overall estimates with their 95% interval and promote interval (the promote level is 1 − 0.01/k), stake, P&L and ROI, and the coverage table's title names the decision times and the maximum input age the params set, so a draft that widened the age says so. For a candidate with more than one league it then prints a per-league table, each league's coverage (`odds_analytics.candidate_backtest.league_coverage`) beside its share of the bets (`odds_analytics.candidate_report.CandidateSummary.leagues`), for information: the verdict is the pooled series'. A low `with_input`, `with_exchange`, `with_polymarket` or `with_retail` count against `decisions` says the range lacks the data for the rule's decision times, which no verdict can repair.

## JSON output

`--json` writes `odds_cli.commands.candidates._backtest_json` of `odds_analytics.candidate_backtest.BacktestResult`, its `dataclasses.asdict` with each summary's `registered` entry replaced by its registry status (a replay scores the draft, so `active`, `promoted` or `killed`): the candidate's name, version, rule, params and hash status, the range, the coverage, the summary (including `odds_analytics.candidate_report.CandidateSummary.family_versions`), the overall estimate, the range's event count (`range_events`), the per-league coverage (`odds_analytics.candidate_backtest.BacktestResult.league_coverage`) and the summary's per-league breakdown (`leagues`), a model rule's tuning, refits and `odds_analytics.candidate_backtest.BacktestResult.library_versions` (the XGBoost, Optuna and NumPy versions, from `odds_analytics.candidate_model.library_versions`), the comparison candidate's result in the same form, or `null`, and `bets`, every bet placed (`odds_analytics.candidate_backtest.BacktestResult.bets`) in placement order, each written by `odds_cli.commands.candidates._bet_json` as its event id, league, kick-off, decision time, outcome, line (`null` in a market without lines), bookmaker, price, close probability and EV, the last two `null` without a close. Dates and enums are written as strings.
