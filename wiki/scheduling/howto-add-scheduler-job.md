# Add a scheduler job

Steps for a new job under `packages/odds-lambda/odds_lambda/jobs/`. Concepts: [Job registry](job-registry.md), [Where each job runs](job-deployment-matrix.md), [Self-scheduling](self-scheduling.md).

1. **Entry point.** Create `jobs/<name>.py` with `async def main(ctx: JobContext) -> None`. When the job is per sport, call `odds_lambda.scheduling.jobs.require_sport(ctx, "<job-name>")` first (a run without a sport must fail, not run every sport) and bail out on unsupported sports. The registry imports job modules lazily by name ([Job registry](job-registry.md#registry)).
2. **Register.** Add one `odds_core.job_specs.JobSpec` to `odds_core.job_specs.JOB_SPECS`, with the lazy module name and entry point. Set its bootstrap override when startup should book a run instead of doing the work. Mark its smoke side effects with `agent_trades`, `candidate_trades` or `paid_api` so deploy smoke requires the corresponding opt-in.
3. **Per sport?** Set `per_sport` and, when restricted, `sports` on the record. Only configured sports in that allowlist get scheduled. A new sport also needs a suffix in `odds_lambda.scheduling.jobs._SPORT_SUFFIX_MAP` (which holds `epl`, `mlb`, `nba` and the football leagues' `championship`, `laliga`, `seriea`, `bundesliga` and `ligue1`); see [Add a sport](../collection/howto-add-sport.md).
4. **Schedule shape.** Pick one:
   - Proximity-driven: use `odds_lambda.scheduling.decision.decide_forward_resilient` or `odds_lambda.scheduling.decision.decide_backward_resilient` with cadence values selected from `odds_core.job_specs.job_cadence`, pre-schedule before the work, re-schedule after, via `self_schedule(job_name=make_compound_job_name(...), ...)`. Pre-schedule first: a job that schedules only after its work loses its chain on any exception, as `check-health` does (#438). Use `odds_lambda.scheduling.collection.run_collection` for an odds collector and choose its postbooking policy from the [table](self-scheduling.md#failure-policy-by-job). Pass `leads` and the run's start time as `run_started` to the decision when the job must also run a set time before each kickoff ([lead runs](decision-engine.md#lead-runs)). A job that creates its own events must not gate on stored events alone: decide through `odds_lambda.collection_calendar.decide_collection_run` (`stored_only` when it only pairs with others' events, `stored_kickoff` when its kickoffs are not the events' `commence_time`), and when `should_execute` is false write the heartbeat and return ([dormancy](decision-engine.md#dormancy)).
   - Fixed local cron: set `cron` on the job record. The two shapes are exclusive: bootstrap re-applies every cron on start, and the local backend refuses a self-schedule for a job with a cron ([bootstrap](local-scheduler.md#bootstrap-jobs-and-cron-table)).
5. **Alerts.** Wrap the work, not the scheduling, in `async with job_alert_context(compound_name):` so a failure sends a critical alert (once per outage, reminding every `stale_reminder_minutes`, which the stale-data check treats as the job's own alert through `odds_core.alerts.job_outage_alerted_at`) and success writes `heartbeat:<compound_name>` ([Alerting and heartbeats](../operations/alerting-and-heartbeats.md#heartbeats), [dedup](../operations/alerts.md#alert-history)). To get a missed-run alert, add the same compound name, with the allowed hours between runs (longer than the overnight pause for jobs that have one; `fetch-mlb-probables` uses 30 h and `fetch-espn-fixtures` and `backup-database` 26 h for their daily runs, `fetch-odds-epl` 49 h for its 48 h opening-tier interval, `fetch-odds-nba` 35 h for its 24 h longest interval plus the quiet window that can push a run to 10:00 UTC, `fetch-oddsportal-nba` 11 h for its 8 h overnight window plus the 2 h interval, `fetch-injuries-nba` 15 h for the up to 14 h its lead runs and 6 h cadence can leave over that window; a dormant job still writes its heartbeat each check-in, so size the expectation to the check-in), to the record's `heartbeats` (one `odds_core.job_specs.Heartbeat` per sport suffix for a per-sport job, such as `fetch-oddsportal-laliga`); `odds_core.config.AlertConfig.heartbeat_expectations` is the operator override. Alerts are silent under `SCHEDULER_DRY_RUN`, so the deploy smoke never pages. Nothing checks that the names match: a key mismatch passes silently, and a job with no heartbeat history is never alerted. A job that writes snapshots also declares an `odds_lambda.collection_calendar.CollectionSource` (the `source` its snapshots are stored under, all `observed`; cadence; an `odds_lambda.collection_calendar.SportCollection` per sport, its fixture horizon and the markets it writes, derived from the job's own per-sport config where it has one) and calls `odds_lambda.collection_calendar.require_rows_for_fixtures` inside the alert context, so a run that stores nothing while fixtures are scheduled fails (fixtures the job saw but rightly did not price go in `accounted_by_sport`), and adds the source to `odds_lambda.health_readers.collection_sources` for the per-market stale-data check and the web UI's status strip ([Stale-data check](../operations/health-monitor.md#stale-data-check)). Checks tied to one job's output, such as the 1x2 close of `fetch-betfair-exchange` for each football league, unsettled events or MLB events without a `gamePk`, are separate methods of `odds_lambda.health_monitor.HealthMonitor`, called from `odds_lambda.health_monitor.HealthMonitor.check_system_health` with its clock, that report after the fact ([Betfair close check](../operations/health-monitor.md#betfair-close-check)). A bootstrapped self-scheduling job is covered by the [schedule chain check](../operations/health-monitor.md#schedule-chain-check); if it returns without booking a run while disabled by a setting, add that setting to `odds_lambda.health_readers.JOB_ENABLED`. The local scheduler cancels a run that exceeds `odds_lambda.scheduling.runner.JOB_TIMEOUT` and re-books a failed run that booked nothing, so the job must finish within the timeout ([Local scheduler](local-scheduler.md#scheduling-primitives)).
6. **Test locally.** `uv run odds scheduler run-once <job>` (compound names work; a global job such as `fetch-mlb-results` takes its bare name), then `uv run odds scheduler start` with the job in `SCHEDULER_BOOTSTRAP_JOBS` ([Local scheduler](local-scheduler.md#cli)).
7. **Run it in production.** Set `bootstrap=True` on its record and redeploy the production host with [deploy.sh](howto-run-scheduler-service.md#redeploy). Registering the job in step 2 creates no schedule, and a registered job left out of the list runs only when `SCHEDULER_BOOTSTRAP_JOBS` names it. The bootstrap list also makes `odds scheduler smoke` run the job on every deploy, unless its record marks smoke side effects. The AWS stack is dormant, so a Terraform rule in `deployment/aws/terraform/eventbridge.tf` is needed only to move production back to AWS; its name must equal the compound name ([Scheduler backends](scheduler-backends.md#rules-and-terraform)).
8. **Docs.** Update [the matrix](job-deployment-matrix.md#where-each-job-runs) and add a wiki page for the job.
