# Test suite

How to run the tests is in [Set up and run locally](howto-develop-locally.md#run-the-tests).

## Layout

```
tests/unit/         ~110 flat files across all six packages; `conftest.py` holds the OddsPortal feed fixtures
tests/integration/  shared fixtures in conftest.py (e.g. an event with child rows (a snapshot with price rows, a paper trade and a match brief), an EPL event with a Betfair `1x2` snapshot without prices, `mixed_source_event` (an EPL event kicking off 2026-04-18 with an Odds API snapshot 3 h out and a later Polymarket one carrying mid, ask and bid price rows), `job_session`, the test session handed to the OddsPortal and Betfair jobs as their session factory, and `fduk_epl` and `fduk_session`, the EPL league and the test session handed to the FDUK loader, reading CSVs from `tests/fixtures/football_data_uk/`, `mlb_schedule`, which scripts the MLB schedule the finder reads, and `replay`, which runs recorded historical responses through the real client and `odds_analytics.backfill_executor.BackfillExecutor`, each call in its own committed session and spending a set acquisition key)
tests/migration/    schema and CLI checks against a real database
tests/fixtures/     sample Odds API JSON; trimmed FDUK CSVs (EPL and La Liga) and the EPL golden load they must reproduce
```

## Configuration

- Class-based tests: pytest is configured with `python_classes = Test*`, `asyncio_mode = "auto"` and `pythonpath = ["scripts"]` (root `pyproject.toml`). Tests that build a naive datetime on purpose carry `# noqa: DTZ001`, because ruff selects the `DTZ` rules for tests too.
- Shared fixtures go in `conftest.py`; `tests/unit/conftest.py` provides `oddsportal_fixtures` (the directory of captured OddsPortal pages under `tests/fixtures/oddsportal/`), `espn_football_scoreboard` (loads the recorded ESPN football scoreboard of a league slug from `tests/fixtures/espn_football/`), `encrypt_payload` (encrypts JSON as the feed does, for synthetic responses) and `make_ml_config` (a small `odds_analytics.training.config.MLTrainingConfig` with a delta target; it carries a tuning section unless called with `tuning=False`). It also provides `edit_source` (makes the code hasher, `odds_lambda.candidate_rules.code_hash.code_sha256`, read a transform of a module's source in place of its file), `fixture_package` (writes the modules of a throwaway first-party package whose import closure the hasher walks), `candidates_repo` (a git repository with an empty `candidates/` directory, for the candidate version check and the rehash command) `git_commit` (commits everything in such a repository), `cross_market_run`, which builds the quotes of one source run's `1x2` and totals snapshots, each with its own age or left out, for the tests of a rule's extra markets and lookback points, `ledger_row` and `INVALID_LEDGER_ROWS`, a complete rehash ledger row and the rows that both the ledger model and the version check must reject, and `holdout_repo`, a committed `candidates/` directory with an empty holdout ledger and, in one commit, the grid file for issue 610's `1x2` version 1 and, in the next, its selection (`preregistration` and `selection` build their data), for the sealed-holdout tests. Other unit tests repeat or import their fixtures.
- `tests/test_helpers.py` builds tagged snapshots: `make_tagged_snapshot` returns a `TaggedSnapshot` dataclass (an envelope's bookmakers, a source tag and, for FDUK, a timing basis), `make_quotes` gives a unit test the `odds_core.quotes.Quote` rows the writers would store for one (both take the `payload_id` of the source run the snapshot belongs to), and `store_tagged` stores it with its price rows through `odds_lambda.storage.shaped_snapshots.store_shaped_snapshot` in an integration test, returning the stored snapshot of its first market. The `add_cross_market_run` fixture in `tests/integration/conftest.py` stores such a run, optionally at a given `created_at`. It also holds `make_epl_event` and `make_nba_event`, which build an event of that sport, `create_scheduler_tables`, which creates the APScheduler data store's tables as the scheduler's first start does, `apply_odds_web_role`, which creates the `odds_web` role and applies its grants file (the `odds_web_session` fixture in `tests/integration/conftest.py` runs it), `as_odds_web` and `as_odds_web_login`, which run each transaction as that role, `client_of`, an HTTP client for the web app, `StubOddsClient`, a stand-in for the Odds API client that returns canned `odds_core.api_models` responses, `RecordedHttpSession`, which serves one recorded historical response through the real client's HTTP layer, `ReplayHttpSession`, which serves a recorded response for each requested date and fails on a date with none, `odds_api_game` and `odds_api_h2h`, which build a historical response's games in the API's shape, `LEAGUE_FIXTURES` and `load_fduk_fixture`, the football fixtures the replay and attach tests share, `FakeMlbStatsFetcher` and `mlb_game`, which script an MLB schedule, and `SessionFactory`, which hands a writer the test session as its session factory, and the gamePk helpers: `with_game_pk` marks an event to hold a gamePk, `hold_game_pks` records it as the event's `mlb_stats_api` external id, and `game_pk_of` reads it back through `odds_lambda.storage.game_pks`. A snapshot added to the session alone has no price rows, so the readers of `odds_core.quotes.quotes` see nothing. `TIER_HOURS_BEFORE` gives each fetch tier an hours-before-kick-off that lands in it.
- `tests/integration/backfill_replay_helpers.py` holds the `BackfillReplay` class and the loaders and constants the backfill replay and guard tests share, and `tests/integration/conftest.py` provides it as a fixture, as it does `add_match` (typed `AddMatch`), which stores an EPL match, completed with a result when given a score, for the fixture-context tests, and `add_cross_market_run` (typed `CrossMarketRun`), which stores one OddsPortal run's `1x2` and totals snapshots under one payload, which replays recorded historical responses, each recorded for a planned snapshot and served at the time the manifest requests it, with each game quoted by Odds API `uk`-region book keys, the neighbouring snapshots' times and a billed `x-requests-last` the test sets per response (nothing for an empty one by default), through the real client and `odds_analytics.backfill_executor.BackfillExecutor`, for its run and probe, and tests of the guards that stop a run, among them a returned snapshot other than the planned one.
- Default run: `testpaths` is `tests/unit` and `tests/integration`, and `addopts` deselects `live_api`, so a bare `uv run pytest` from the repo root runs the offline suite and never collects `tests/migration` (root `pyproject.toml`). Run from a subdirectory, pytest ignores `testpaths` and collects from that directory. A path on the command line replaces `testpaths`; a second `-m` replaces the `addopts` one, so `-m live_api` selects the live tests and any other `-m` expression drops the `live_api` exclusion, while a live-API test named by path alone is still deselected.
- PGlite serves one connection at a time and answers over `psycopg` only, so tests that need a second connection to it, such as the web UI's (the portfolio, candidate and data-health pages, the status strip and the readers behind them, its dead-chain check over scheduler tables that `tests.test_helpers.create_scheduler_tables` creates), share the suite's engine and take the `odds_web` role with `SET LOCAL ROLE` after applying the grants file (`tests/integration/test_odds_web_database.py`, `tests/integration/test_odds_web_data_health.py`, `tests/integration/test_odds_web_readers_under_role.py`; [odds-web](../operations/odds-web.md#database-access)). PGlite does not enforce `statement_timeout`, so no test there can show a query cancelled by the web engine's timeout, and its psycopg errors are classed differently from production's asyncpg ones, so `tests/unit/test_odds_web_cache.py` builds asyncpg-shaped errors, wrapped in a bare `DBAPIError` or raised raw as at connect time, for `odds_web.cache.failure_kind`. `tests/integration/test_odds_web_readers_under_role.py` renders every page and fragment from rows of each sport (decision rows carrying their candidate's league set) under the role, revokes each table in `odds_web.role_check.READ_TABLES` in turn to show some page fails, and checks that the grants file lists exactly those tables, so a reader that starts using an ungranted table fails the suite. `odds_web.role_check` is tested the same way, with the role's read-only default applied to each transaction because `SET ROLE` does not apply it. `tests/unit/test_deploy_script.py` runs `deploy.sh` against stand-in `git`, `uv`, `sudo` and `systemctl` commands that log each call, with a pseudo-terminal as stdin for the paths that differ with a terminal attached.
- Markers: `integration` tags tests in `tests/integration` (most run on py-pglite, and no run selects on it), and `live_api` tags tests that call third-party HTTP APIs, which the scheduled live-API workflow runs (`.github/workflows/live-api.yml`). On each push that changes more than the wiki, docs or Markdown files, or that changes the how-to page whose example draft `tests/unit/test_candidates.py` parses and resolves, CI runs the default run on the interpreter `uv sync` picks from `requires-python` ([CI/CD workflows](../operations/ci-cd-workflows.md)) and, before the tests, a `deptry` check per package for undeclared imports (`.github/workflows/test.yml`, [Dependency checks](code-conventions.md#dependency-checks)).
- Importing the jobs, the CLI or `odds_core.alerts` builds settings (`tests/conftest.py`'s `mock_settings` fixture builds its own, with per-sport bookmakers for NBA only), so tests need a `DATABASE_URL`: pytest-env (`env` in the root `pyproject.toml`) sets `ODDS_API_KEY` to an empty string, overriding the shell (an `ODDS_API_KEYS` list in the environment or `.env` still takes precedence in `odds_core.config.APIConfig.keys`), and CI supplies `DATABASE_URL` from a secret ([Workspace packages](workspace-packages.md#odds-core)). It overwrites `DISCORD_WEBHOOK_URL` and `DEAD_MANS_SWITCH_URL` with empty values and `ALERT_ENABLED` with `false`, so a webhook or monitor in the developer's shell or `.env` never receives test alerts or pings.

## Unit and integration databases

`tests/unit` and `tests/integration` use an in-process PostgreSQL (py-pglite) on automatically allocated TCP ports. `tests/conftest.py` forces TCP and routes manager startup through `start_pglite_manager`, which retries port collisions, confirms the spawned server owns its listener, waits for PGlite readiness before opening the socket server and adds Node's `--liftoff-only --wasm-lazy-compilation` flags to keep startup within the test host's memory budget. This follows PGlite's documented [socket initialization](https://pglite.dev/docs/pglite-socket) and [`waitReady` API](https://pglite.dev/docs/api). The session fixture creates all SQLModel tables once; `pglite_async_session` truncates every table (`RESTART IDENTITY CASCADE`) before each test and restarts the events identity at 1,000,001, so a test can give an event a small literal id, and yields an `AsyncSession` with `expire_on_commit=False`. Aliases `test_engine` and `test_session` exist for older tests, and `gamma_event` and `gamma_nba_event` build a Gamma EPL and NBA match event for Polymarket tests. Independent pytest processes can run concurrently ([AGENTS.md](../../AGENTS.md#tests)). Fixtures for Odds API payloads live under `tests/fixtures/`. `recorded_mlb_schedule` loads a recorded 2024 MLB Stats API schedule (`tests/fixtures/mlb_stats_api/schedule_2024.json`: postponed, cancelled and resumed games and both kinds of doubleheader among others), and `recorded_mlb_fetcher` is an `odds_lambda.mlb_stats_fetcher.MlbStatsFetcher` that serves it by date range. The legacy snapshot conversion tests use the same startup fixture with a separate pglite engine on its own TCP port, a transaction-scoped legacy schema and migration operations bound directly to that connection. They never use `DATABASE_URL` as their connection target.

## Migration tests

`tests/migration` connects to whatever `DATABASE_URL` points at and replaces `odds_core.database.async_session_maker` with a `NullPool` session factory in `pytest_configure`. Only the deploy workflows run it, each after `terraform apply`: dev runs all of it, prod runs `test_schema_validation.py` and `test_cli_readonly.py` ([CI/CD workflows](../operations/ci-cd-workflows.md)). A bare `uv run pytest` does not collect it; it runs only when named by path, as in `uv run pytest tests/migration -v` ([Databases and environments](databases-and-environments.md#environments)).
