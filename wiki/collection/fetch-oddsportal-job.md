# The fetch-oddsportal job

`odds_lambda.jobs.fetch_oddsportal.main(ctx)` reads pre-match odds over HTTP ([oddsportal-scraper](oddsportal-scraper.md)), converts them to the canonical shape and stores one snapshot per market with its price rows through `odds_lambda.storage.writers.OddsWriter.store_envelope`, and a snapshot already stored under its key is skipped ([Writing price rows](../storage/price-tables.md#writing-price-rows)). It is in the default local `bootstrap_jobs` and runs on the production host ([job-deployment-matrix](../scheduling/job-deployment-matrix.md#where-each-job-runs)). It has no Terraform rule or Lambda; a rule left in the AWS account from before their removal would scrape alongside the production host, and no code checks for a job enabled in both places. Deployed state: `odds scheduler list-jobs --backend aws`. On the production host, one hung run ends the local chains (#485).

## Leagues

`odds_lambda.jobs.fetch_oddsportal.LEAGUE_SPECS` holds `odds_lambda.jobs.fetch_oddsportal.LeagueSpec` rows, each with a 48 h fixture horizon: six football leagues with markets `1x2` and `over_under_2_5`, 3 outcomes and overnight 22-06 (EPL `england-premier-league`, listing `/football/england/premier-league/`; Championship `england-championship`, `/football/england/championship/`; La Liga `spain-laliga`, `/football/spain/laliga/`; Serie A `italy-serie-a`, `/football/italy/serie-a/`; Bundesliga `germany-bundesliga`, `/football/germany/bundesliga/`; Ligue 1 `france-ligue-1`, `/football/france/ligue-1/`), MLB (`mlb`, listing `/baseball/usa/mlb/`, market `home_away`, 2 outcomes, overnight 05-14) and NBA (`nba`, listing `/basketball/usa/nba/`, markets `home_away`, `totals_ladder` and `spreads_ladder`, 2 outcomes, overnight 07-15; the ladders store each game's main line and its neighbours as [ladder markets](oddsportal-scraper.md#ladder-markets)). OddsPortal lists NBA games by full team name, which are the canonical names. `ctx.sport` is required and only its spec runs; a missing league raises `ValueError` and an unknown league logs an error and returns. The job reads its overnight window from `odds_lambda.scheduling.decision.OVERNIGHT_WINDOWS` by the spec's league ([decision-engine](../scheduling/decision-engine.md#overnight-windows)). NBA events come from the ESPN NBA schedule (#725), so the NBA job stays dormant until that is scheduled, and the events of the five football leagues other than the EPL come from the [ESPN football schedule](espn-football-schedule.md).

## Flow

Scheduling follows the [shared collector lifecycle](../scheduling/self-scheduling.md#pattern). OddsPortal postbooks after the successful heartbeat only when events were scraped.

1. Pre-schedule using `odds_lambda.collection_calendar.decide_collection_run` with `odds_lambda.jobs.fetch_oddsportal.CADENCE`, timed from the events' `commence_time` ([decision-engine](../scheduling/decision-engine.md#cadence)), and the [candidate leads](#runs-before-candidate-decisions). With no event in the stored events or the league's published schedule within 28 days the run is dormant, the same decision for every collector: it books a 6 h check-in (or the moment a known event enters the 28 days), writes its heartbeat and returns without scraping ([dormancy](../scheduling/decision-engine.md#dormancy)). A scheduler restart keeps the pre-scheduled run ([bootstrap](../scheduling/local-scheduler.md#bootstrap-jobs-and-cron-table)).
2. Inside `job_alert_context(compound_name)`, `odds_lambda.jobs.fetch_oddsportal.ingest_league` per spec: `odds_lambda.jobs.fetch_oddsportal.scrape_league` (listing, book context, then one feed per upcoming event and market, converted by `odds_lambda.oddsportal_adapter.convert_market` with the feed's decimal prices kept as `price_decimal` and the OddsPortal event id as the envelope's `oddsportal_event_id`; a failed event or market is recorded in the stats errors and skipped, but a league where every market fetch failed raises `odds_lambda.oddsportal_client.OddsPortalError`, as does a listing with no events and no empty-state marker), one payload archiving the run's envelopes, the event of each game through `odds_lambda.live_events.LiveEventFinder.resolve` (shared with the Odds API writers) and the [event resolver](../storage/event-resolver.md), recording the OddsPortal event id (which never merges; a game naming a team outside its league's canonical teams is dropped, [refused team names](../storage/event-matching.md#refused-team-names); for MLB, one MLB schedule request per run resolves every listed game to its `gamePk` before the database session opens, and a game left unresolved gets no event or snapshot and is counted in `games_unresolved`, [live MLB events](../storage/event-matching.md#live-mlb-events)) and `odds_lambda.storage.writers.OddsWriter.store_envelope` per event under its integer id, which stores each market's snapshot once per key (source `oddsportal`, time basis `observed`; tiers are derived, see [fetch-tier](../storage/fetch-tier.md)). Events are resolved and stored in fixture-lock order, each in its own savepoint, so a failed event is recorded in the errors and the others are kept. A league failure, including those errors, is logged and the others continue.
3. A run that dropped MLB games (unresolved, or skipped while the MLB schedule was unavailable) sends the `games_dropped:<job>` warning (`odds_lambda.live_events.alert_dropped_games` with its default `stored="odds"`, [alerts](../operations/alerts.md#alert-history)), which never fails the run. If any league failed, the job raises after the others finish. Otherwise `odds_lambda.collection_calendar.require_rows_for_fixtures` raises `odds_lambda.collection_calendar.EmptyCollectionError` for a league with zero stored snapshots and a SCHEDULED event within 48 hours (`odds_lambda.jobs.fetch_oddsportal.SOURCE`, whose snapshots are source `oddsportal`, time basis `observed`, with the horizon and the markets each `odds_lambda.jobs.fetch_oddsportal.LEAGUE_SPECS` entry scrapes, through `odds_lambda.jobs.fetch_oddsportal.league_collection`, built once at import by `odds_lambda.jobs.fetch_oddsportal.collection_source`; MLB events come from the MLB Stats API schedule, [stale-data check](../operations/health-monitor.md#stale-data-check)), with the run's scrape errors in the message. Both fail inside [`odds_core.alerts.job_alert_context`](../operations/alerts.md#delivery): a critical alert (once per outage) and no heartbeat ([empty collection](../operations/alerting-and-heartbeats.md#empty-collection)). A league with no events in that window passes, and so does one whose listing parsed with events but every listed event had already started (`odds_lambda.jobs.fetch_oddsportal.IngestionStats.events_listed` above zero, `odds_lambda.jobs.fetch_oddsportal.IngestionStats.upcoming_listed` zero): no scrapeable event existed, so the job logs `oddsportal_empty_run_check_skipped` (a warning carrying the latest listed start time) and leaves that league out of the check (it passes no `accounted_by_sport`, which only the [Betfair job](betfair-exchange.md) uses). A listing with no events and no empty-state marker, a league with an upcoming event that stored nothing, and an empty-state listing while events are scheduled still raise.
4. Post-schedule only when at least one event was scraped. A zero-event run skips it, so the next run keeps the earlier computed time.

## Runs before candidate decisions

A [rule candidate](../evaluation/candidate-rules.md#market-state) decides from a recent snapshot carrying retail and Betfair Exchange prices together, as a live OddsPortal snapshot does, at its decision time and at each [lookback point](../evaluation/candidate-rules.md#lookback-points). `odds_lambda.jobs.fetch_oddsportal.candidate_scrape_leads` takes the process's registry snapshot, read when the scheduler started ([when the registry is read](../evaluation/candidate-registry.md#when-the-registry-is-read)), and, through `odds_lambda.candidate_rules.registry.input_leads`, takes every decision time in the `minutes_before_kickoff` list of every active rule candidate whose `leagues` include the job's league and whose rule and params resolve, whatever its `start_date` ([decision times](../evaluation/candidate-rules.md#decision-times)), and every lookback point of each decision time. Each becomes a [lead](../scheduling/decision-engine.md#lead-runs) `odds_lambda.jobs.fetch_oddsportal.SCRAPE_LEAD` (5 min) before that time that still runs late until it: a run that much before every stored kick-off, inside the overnight window too. A run at the time itself would not serve a lookback point, because its snapshots are stamped a few seconds after it starts and a point reads only snapshots stamped at or before it. The job passes its start time, so a cadence run that started before a lead time and finished after it books the lead run straight away. A run during which a listed event is awaiting one of those times (`odds_lambda.jobs.fetch_oddsportal.awaiting_decision`: its kick-off lies between the lead's time and its run time, plus `odds_lambda.scheduling.decision.MIN_LEAD_RUN_GAP`) is a pre-decision run. `odds_lambda.jobs.fetch_oddsportal.scrape_league` then scrapes only those events, and after the listing its requests go ahead of other runs' waiting requests at the process's request pacer ([request pacing](oddsportal-scraper.md#request-pacing)). Every OddsPortal request of the scheduler process shares that pacer, one request a second, so leagues whose runs start in the same minute take turns, and a run stores its snapshots only once its scrape ends. On 2026-11-11 the six football leagues scraped together (236 requests, every one HTTP 200) took 4 minutes. With priority, a pre-decision EPL run for five events, contending with the five other football leagues and MLB and NBA runs (333 requests), finishes its scrape 12 s after it starts in the unit test, against the 5 minute lead, so its snapshots are about 5 minutes old at the decision. In a process whose first read of the registry finds it unreadable, such as `odds scheduler run-once`, it logs `candidate_registry_invalid` and adds no runs, so collection keeps its cadence. Events that kick off together share a run.

## Heartbeats

Heartbeats are keyed `heartbeat:fetch-oddsportal-<suffix>`, one per league in the `heartbeats` field of its `odds_core.job_specs.JOB_SPECS` record: 11 h for each football league and NBA and 12 h for MLB, covering the overnight window. They share the map in `odds_core.config.AlertConfig.heartbeat_expectations` with every other job's ([alerting-and-heartbeats](../operations/alerting-and-heartbeats.md#heartbeats)).
