# Event merge

A match must be one `events` row, because rows that join prices from several sources key on `event_id`. Each source names a match by its own id, held as an [external id](events.md#external-ids), so one match can exist as several events (twins). `odds_lambda.storage.event_merge.EventMerger` is the only code that collapses them.

## Kept event

When nothing else decides which event of a match to keep, `odds_lambda.storage.event_merge.kept_event` keeps the one holding an external id from the source its sport's [kick-off authority](kickoff-authority.md) order (`odds_lambda.storage.event_kickoff.KICKOFF_AUTHORITY`) ranks highest (for NBA: OddsPortal, the Odds API, then ESPN), since the kept event keeps its own commence time and that source's kick-off is the best. Events no ranked source names (a football-data.co.uk event holds no id) come last, and ties go to the first stored (`odds_lambda.storage.event_merge.first_stored`, the lowest integer id). Jobs find an event by its external ids, so which event's id survives does not matter to them.

Events holding different MLB `gamePk`s (`mlb_stats_api` external ids, `odds_lambda.storage.game_pks.game_pks_of`; [Event matching](event-matching.md#mlb-gamepk-resolver)) are different games, so they are never twins and never merge.

## Finding and merging are separate

The finders only read. `odds_lambda.storage.event_merge.find_match_id` (±2 h, used by `odds_lambda.live_events.LiveEventFinder.fixture_key`) returns the candidate `odds_lambda.storage.event_merge.kept_event` picks; `odds_lambda.storage.event_merge.find_match_candidates` returns every candidate, for the [event resolver](event-resolver.md#steps) and the MLB claim rules ([live MLB events](event-matching.md#live-mlb-events)). `odds_lambda.storage.event_merge.find_historical_candidates` (±24 h, same sport) returns every candidate for the historical loaders, which the resolver reduces to a lone candidate or the nearest within ±2 h ([Event resolver](event-resolver.md#steps)), so neighbouring fixtures of the same teams (an NBA back-to-back) are never conflated. No finder merges or deletes.

Merging happens in three places only:

| Caller | Entry point |
|---|---|
| `odds events repair-names --apply` | `odds_lambda.storage.event_name_repair.repair_team_names`: fixes annotated, cut-off and `Game N` team names of every event of the sport, taking full Betfair runner names from the snapshot payload of each event's latest Betfair snapshot (`snapshot_payloads`; a run payload's envelope is the one carrying the event's Betfair id, or one it was refused, replaced or dropped for in `data_quality_logs`, and an event whose envelope is not found is logged as `betfair_envelope_not_found`; and a database copied with `odds copy from-prod` has no payloads, so only the name cleaning applies there), then merges each resulting twin group into the event `odds_lambda.storage.event_merge.kept_event` picks among those never renamed |
| `odds events merge-twins --apply` | `odds_lambda.storage.event_merge.EventMerger.merge_group` for every twin group, keeping the event `odds_lambda.storage.event_merge.kept_event` picks |
| `odds events assign-game-pks --apply`, `odds events set-game-pk --merge --apply` | `odds_lambda.storage.game_pk_backfill.apply_assignment`: the events of one MLB `gamePk` ([Assigning gamePks](#assigning-gamepks)) |

The production copier does not merge. It replaces the rows of the one local event it matched (by external id or fixture; a fixture match holding a different id from one of the production event's sources is refused, [copying](../foundations/databases-and-environments.md#copying-production-data)), so merging a local twin into that event first would delete the twin's own rows (football-data.co.uk, Polymarket, Betfair history) with the replaced ones, and a scraper event could absorb an Odds API event. It leaves local twins in place and reports how many matches have them.

## Merging

`odds_lambda.storage.event_merge.EventMerger.merge_drops` counts, read-only, the rows a merge would delete (the clashing decisions and their trades, external ids and acknowledgements below), so a caller can refuse a merge before it runs.

`odds_lambda.storage.event_merge.EventMerger.merge` re-points every foreign key to `events`, all of which reference `events.id` (external ids and health-check acknowledgements included). Before re-pointing, it deletes the duplicate's external ids from a source the kept event has an id from, and its acknowledgements of a check the kept event is acknowledged for, logging each as `merge_dropped_external_id` or `merge_dropped_acknowledgement` with a `data_quality_logs` row (`odds_lambda.storage.event_merge.EventMerger._drop_clashing_identity_rows`) and counting them in the report's deleted rows. A moved snapshot's tier follows the kept event's kick-off, since tiers are derived ([Fetch tier](fetch-tier.md)). It also copies status, scores and `completed_at` from a duplicate when the kept event has no scores (logging `merge_conflicting_scores` when both have different ones), and deletes the duplicates. When the events hold more than one distinct `gamePk` it raises `odds_lambda.storage.event_merge.ConflictingGamePks` before changing anything; otherwise a kept event with no `gamePk` takes its duplicate's, since the `mlb_stats_api` external id moves with the other references. Every merge path goes through it, so `odds events merge`, `merge-twins` and `repair-names` all refuse to merge two games. A mechanical candidate version decides a match once per entry of its decision times (`odds_core.paper_trade_models.CandidateDecision.minutes_before_kickoff`) and bets each outcome once ([once per selection](../evaluation/candidate-rules.md#once-per-selection)), so when both events hold a `odds_core.paper_trade_models.CandidateDecision` for one candidate version the kept event's decisions win: all of the duplicate's decisions of that version, and the paper trades that reference them, are deleted (`odds_lambda.storage.event_merge.EventMerger._drop_clashing_decisions`, logged as `merge_dropped_clashing_decisions` with the counts). Every other decision and trade moves with the foreign keys. A decision's `input_snapshot_ids` (the snapshot it decided from) are plain integers, not foreign keys, so a merge leaves them as recorded and the parity check still loads exactly that snapshot ([parity check](../evaluation/candidate-parity.md#replay-of-a-decision)). The foreign keys are read from the PostgreSQL catalog (`odds_lambda.storage.event_merge.EventMerger._event_reference_columns`), so every referencing table is covered whichever models the process imported. When the kept event holds a `gamePk` afterwards, its `missing_mlb_game_pk` acknowledgement and UNMATCHED status are cleared (`odds_lambda.storage.event_unmatched.clear_unmatched`). It runs in the caller's transaction and logs `events_merged` with the rows moved per table.

## Detection

No database constraint forbids twins. `odds_lambda.health_monitor.HealthMonitor.check_event_identity` runs on every check-health run ([health monitor](../operations/health-monitor.md)) and raises one warning per sport and kind, none merging anything:

- **Twins** (`duplicate_events:<sport>`): `odds_lambda.storage.event_merge.EventMerger.find_twin_groups` clusters events with the same sport and teams whose commence times are within ±2 h of the cluster's first event. A cluster holding different `gamePk`s is two games, so it is left out and logged as `twin_group_conflicting_game_pks`.
- **Repeated fixtures** (`repeated_fixtures:<sport>`): `odds_lambda.storage.event_merge.EventMerger.find_repeated_fixtures` finds a home and away pair stored more than once in a season (August to July) further apart than ±2 h, for `odds_lambda.health_monitor.LEAGUE_SPORTS`. This is a rescheduled match stored as a second event.
- **MLB events without a gamePk** (`missing_game_pk:baseball_mlb`): `odds_lambda.health_monitor.HealthMonitor.find_mlb_events_without_game_pk` lists MLB events created more than `odds_lambda.health_monitor.GAME_PK_GRACE` (24 h) ago holding no `gamePk` and no `missing_mlb_game_pk` acknowledgement (set by `odds events mark-unassignable`). Only events created at or after the earliest-created event that holds a `gamePk` count, so events stored before the live jobs assigned `gamePk`s are left out; while no event holds one the check is silent. The alert lists the event ids and reminds once a day (`odds_lambda.health_monitor.GAME_PK_ALERT_INTERVAL`).

## Assigning gamePks

`odds events assign-game-pks [--since DATE] [--apply] [--delete-ghosts]` (`odds_cli.commands.events.assign_game_pks`) gives MLB events stored without a `gamePk` theirs; the steps are on [Assign MLB events their gamePk](howto-assign-mlb-game-pks.md).

- **Planning** (`odds_lambda.storage.game_pk_backfill.plan_game_pks`, read-only): every MLB event holding no `gamePk` and no `missing_mlb_game_pk` acknowledgement (`odds_lambda.storage.event_unmatched.unmatched_reasons`; a FINAL event keeps its status when marked, so the acknowledgement is read rather than the UNMATCHED status), on or after the `--since` MLB date (US Eastern), is resolved by the [MLB gamePk resolver](event-matching.md#mlb-gamepk-resolver) with no game number. A team pair's events on one MLB date whose starts lie within `odds_lambda.mlb_game_resolver.START_MATCH_WINDOW` of the earliest of them are one row at that start, so twins of one game are never paired with two games by start order. The rows are resolved against one schedule fetch from the earliest of their MLB dates to today, so a postponed game's played slot is in it. Events that already hold a `gamePk` on the same team pair and MLB date are resolved alongside, so a doubleheader pairs by start order; when one of them resolves to a game other than its own, the date's events without a `gamePk` stay unresolved (`held_game_mismatch`). The events resolved to one `gamePk` form one assignment with the event already holding it, if any. The game's played slot (`odds_lambda.mlb_game_resolver.played_slots`) is the slot neither postponed, cancelled nor a resumed continuation, TBD or not. The kept event is the holder; else, among the events on the played slot's MLB date when there are any, so a postponed slot's event never wins over one on the played date, the event nearest the played slot's start (MLB's placeholder when the start is TBD), ties going to the latest and then to the first stored (`odds_lambda.storage.event_merge.first_stored`); with no played slot yet, the first stored. The rest are merged into it. An unresolved `no_game` event that no table references is a ghost.
- **Applying** (`odds_lambda.storage.game_pk_backfill.apply_assignment`): `odds_lambda.storage.event_merge.EventMerger.merge` merges the others into the kept event; merged events' paper trades, match briefs and candidate decisions move with every other foreign key. A merge that would delete anything, which every merge does to a candidate decision the kept event also holds ([Merging](#merging)), raises `odds_lambda.storage.game_pk_backfill.MergeClash` and the game is refused instead. The kept event then takes the `gamePk` and moves to `odds_lambda.storage.game_pk_backfill.GamePkAssignment.target_start` (`odds_lambda.mlb_game_resolver.PlayedSlot.start_for` of the played slot) (`odds_lambda.storage.event_kickoff.move_kickoff` on the MLB Stats API's authority, the step the live jobs take; a POSTPONED event becomes SCHEDULED; [Kick-off authority](kickoff-authority.md)). That is the scheduled start; when the start is TBD, an event already on the played date stays at its listed time, a better estimate than MLB's placeholder, and one elsewhere (a postponed slot's event) moves to the placeholder, so it sits on the date the game was played. When MLB lists the game as Final (`odds_lambda.mlb_game_resolver.final_scores`) and the kept event has no score, `odds_lambda.storage.writers.OddsWriter.update_event_status` settles it FINAL with MLB's home and away score, so a postponed slot moved onto a played game is not left unsettled; a stored score that differs from MLB's is left alone. No snapshot is deleted. The kick-off move takes the current time as the clock, and the MLB Stats API may move the event to a past start; ranking first, it is not held to the rule that football-data.co.uk moves only events no other source observed.
- **Transactions** (`odds_lambda.storage.game_pk_backfill.run_assignments`): each assignment runs in its own savepoint. A refused game, or one that raises anything (a unique-index violation from a `gamePk` a live job took meanwhile, say), rolls back that game only, is logged and is reported as `REFUSED` or `FAILED`; the rest go ahead. With `--apply` each game commits on its own, so a second run finds nothing left to assign; without it everything is rolled back at the end, so the dry run runs the same code and reports exactly what `--apply` would do. `--delete-ghosts` with `--apply` deletes the ghosts (`odds_lambda.storage.game_pk_backfill.delete_ghosts`, which skips any that something references by then).
- **Output**: a summary (events without a `gamePk`, singles, merge groups and those that move paper trades, match briefs or candidate decisions, events settled from MLB, score conflicts, refusals, failures, unresolved by reason, ghosts, events marked unassignable), then one line per item, each starting with its kind: `SINGLE`, `MERGE`, `MERGE_READ_ONLY` (a merge that moves `odds_lambda.storage.game_pk_backfill.READ_ONLY_TABLES` rows), `REFUSED` (`reason=paper_trade_clash` with the rows it would delete), `FAILED`, `UNRESOLVED`, `GHOST` and `UNASSIGNABLE`. An applied line gives the `gamePk`, the kept id, the resolver rule, `moved_from=<old>→<new>` (or `moved=no`), `start=tbd` when the played start is TBD, `score=` (`none`, `kept`, `carried` from a merged event, or `conflict:` with the differing scores, `odds_lambda.storage.game_pk_backfill.ScoreCarry`), `settled=` (`mlb`, `matches`, `conflict:stored_…_vs_mlb_…` or `no`, `odds_lambda.storage.game_pk_backfill.Settlement`); a merge line adds the merged ids and the rows moved per table. With `--delete-ghosts` but no `--apply` it prints how many ghosts would be deleted.

`odds events set-game-pk EVENT_ID GAME_PK [--merge] [--apply]` (`odds_lambda.storage.game_pk_backfill.plan_hand_assignment`) assigns one event by hand. It reads the game's slots (`odds_lambda.mlb_stats_fetcher.MlbStatsFetcher.fetch_game`), refuses an event that holds a `gamePk`, an unknown game, a game of other teams, and a game with no slot on the event's MLB date or within `odds_lambda.mlb_game_resolver.MAX_SINGLE_GAME_GAP` of its start (a typo naming another series), takes the played slot from `odds_lambda.mlb_game_resolver.played_slots` and the Final score from `odds_lambda.mlb_game_resolver.final_scores`, and refuses a `gamePk` another event holds unless `--merge`, which merges the event into that holder. It then applies like the backfill.

`odds events mark-unassignable EVENT_ID --reason TEXT [--apply]` (`odds_lambda.storage.game_pk_backfill.mark_no_game_pk`) marks an MLB event without a `gamePk` as having no game: `odds_lambda.storage.event_unmatched.mark_unmatched` sets its status UNMATCHED and stores the reason as its `missing_mlb_game_pk` health-check acknowledgement ([Events table](events.md#health-check-acknowledgements)), which the `missing_game_pk` warning and the backfill read; the backfill lists the event as `UNASSIGNABLE`. A FINAL event keeps its status and takes only the acknowledgement. Giving the event a `gamePk` later deletes the acknowledgement and makes an UNMATCHED event SCHEDULED again (`odds_lambda.storage.event_unmatched.clear_unmatched`).

## Command

`odds events merge-twins [--sport SPORT] [--apply]` (`odds_cli.commands.events`, which also holds `sync-nba-games`) prints the number of matches with twins per sport and in total. Without `--apply` it writes nothing. With it, the groups are merged in one transaction and the remaining count is printed. `odds events repair-names [--sport SPORT] [--apply]` (default `baseball_mlb`, `odds_cli.commands.events`) fixes the annotated ("(D Rasm"), cut-off ("St. Louis Cardin") and `Game N` team names of every event of the sport with `odds_lambda.betfair.adapter.canonical_teams`, against the full runner names in the payload of the event's latest Betfair snapshot where it has one. It prints each merge group as the kept id with its status, then the ids merged into it, and the count of events renamed in place. An event with no twin within ±2 h keeps its id and takes the new name, so the results job can settle it. Doubleheader games in production start 4 to 6 h apart, so they stay separate events; a doubleheader listed less than 2 h apart merges only when at most one of its games holds a `gamePk`. Without `--apply` the whole plan runs and is rolled back; running it again changes nothing. (`odds events sync-nba-games`, also in `odds_cli.commands.events`, creates no twin: it matches a played NBA game to an existing event before creating one, [NBA games already played](../collection/polymarket-odds-snapshots.md#nba-schedule-from-espn).) It never merges repeated fixtures; `odds events merge KEEP_ID DROP_ID [--apply]` merges one named pair (same sport and teams required, the two ids must differ, dry run without `--apply`), for a rescheduled match that `repeated_fixtures` flags. Keep the event with the real kick-off and result. `odds events repair-scores` (same module) corrects the scores of FINAL MLB events (each paired with the game its `gamePk` names) and never merges or deletes ([results jobs](../collection/results-jobs.md#verifying-mlb-scores)).
